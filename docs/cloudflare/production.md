# Bascule de production

La bascule a été exécutée avec autorisation le 11 septembre 2026. Le Worker `dropthing-production` sert directement `dropthing.mtnz.app` comme Custom Domain, sans origine VPS, D1 contient les 42 lignes historiques et le Cron tourne toutes les cinq minutes. Le VPS `ks17` (46.224.197.187) a ensuite été décommissionné : Coolify, le frontend et la base PostgreSQL legacy, ainsi que les sauvegardes de bascule qui y étaient stockées, n’existent plus. D1 et R2 sont désormais la seule source ; toute sauvegarde doit être conservée hors du serveur de production.

La conversion en Custom Domain a d’abord échoué silencieusement : `wrangler deploy` renvoie `100117` tant qu’un A externe occupe le hostname, et le trafic est resté porté par la route `dropthing.mtnz.app/*`. Le 11 septembre 2026, les A apex et `api.dropthing.mtnz.app` vers le VPS ont été supprimés, le Custom Domain attaché (record Workers `AAAA 100::`, certificat émis) puis la route supprimée.

1. Identifier la branche principale GitHub effective et relier Cloudflare Workers Builds à celle-ci. Build command : `bun install --frozen-lockfile && bun run type-check && bun run lint && bun run test && bun run build`. Deploy command : `bunx wrangler d1 migrations apply <DB> --remote --config apps/api/wrangler.production.jsonc && bunx wrangler deploy --config apps/api/wrangler.production.jsonc`. Les migrations ne font jamais de transfert/reset.
2. Copier `wrangler.production.example.jsonc` vers un fichier de production validé en remplaçant tous les `REPLACE_ME`. Ne jamais recopier UUID/config Bara. Exécuter depuis un checkout vierge et vérifier `apps/api/.local-data/build/index.js`. Neutraliser les variables Workers Builds qui demanderaient à Wrangler de réécrire la config ; refuser toute proposition automatique.
3. Sauvegarder PostgreSQL et D1. Le bucket existant confirmé est `dropthing`, son domaine public est `cdn-dropthing.mtnz.app` et son CORS autorise déjà PUT + Content-Type depuis localhost:5179 et dropthing.mtnz.app. Confirmer encore le préfixe historique complet avant de remplir la configuration. Définir `GROQ_API_KEY`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` comme secrets Worker interactifs, jamais dans Git/logs.
4. Déployer/migrer le schéma compatible avant la bascule, mais garder le trafic sur le VPS. Tester un environnement de développement distant : SigV4 PUT, CORS, tailles réelles, chiffrement, annulation de flux et liens.
5. Exécuté : l’API VPS a été arrêtée avant l’extraction finale. Les deux extractions ont produit la même empreinte ; l’import D1 a préservé 42/42 lignes, dont les contenus supérieurs à la limite d’une instruction SQL grâce à une reconstruction par fragments bornés.
6. Exécuté : route et Cron activés. Health, assets, création/lecture/suppression texte, upload direct, contrôle de taille, confirmation, streaming chiffré et suppression ont été validés sur le domaine. Les données synthétiques ont été nettoyées ; D1 contenait ensuite 42 drops et zéro intention.
7. Exécuté : routage finalisé par Custom Domain. Vérifié le 11 septembre 2026 — le DNS public ne renvoie plus que des adresses Cloudflare, aucun record ne pointe vers le VPS, le Custom Domain `dropthing.mtnz.app` est attaché à `dropthing-production` (`enabled`), la route `dropthing.mtnz.app/*` est absente, et `/api/health` ainsi que les routes API répondent depuis le Worker.
8. Exécuté : VPS `ks17` décommissionné le 11 septembre 2026. Coolify, le frontend et la base PostgreSQL legacy, l’ancien enregistrement DNS `coolify.mtnz.app` et la GitHub App de synchronisation `dropthing-lucas` ont été supprimés. Le Worker `dropthing-production` et son Custom Domain restent la seule cible de production.

Retour arrière : le VPS n’existant plus, un retour à l’origine PostgreSQL n’est plus possible. Pour une version antérieure du Worker, redéployer depuis **Workers & Pages → dropthing-production → Deployments**. Pour la base, D1 Time Travel ne couvre qu’une fenêtre limitée ; au-delà, restaurer depuis un export D1. La suppression d’objets R2 est irréversible sans sauvegarde. La décision de rollback doit donc précéder l’activation du cleanup, et des exports réguliers de D1 et R2 doivent être conservés.

Coûts : R2 n’est pas illimité ; le [palier gratuit actuel](https://developers.cloudflare.com/r2/pricing/) comprend 10 GB-mois et des quotas d’opérations, qu’un petit nombre de fichiers de 3 Go peut dépasser. D1 est limité par base (10 GB payant, 500 MB gratuit au 11 septembre 2026) et Workers a ses propres limites CPU/mémoire/requêtes. Revalider les [limites Workers](https://developers.cloudflare.com/workers/platform/limits/), [D1](https://developers.cloudflare.com/d1/platform/limits/) et [tarifs R2](https://developers.cloudflare.com/r2/pricing/) le jour de la bascule. Groq reste externe. Ne souscrire aucune offre payante sans autorisation.
